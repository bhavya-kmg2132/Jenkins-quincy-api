1. Executive Summary

This document describes the architecture of an enterprise-grade .NET 10 microservices platform built on Clean Architecture, CQRS, and event-driven design principles. The platform is organised around discrete business domains — core operations, notifications, and workflow orchestration — each deployed as an independent, loosely coupled service behind a unified Ocelot API Gateway.

Key architectural highlights:

  • API-First: Single Ocelot gateway is the sole entry point — enforces auth, routing, rate limiting, and caching.
  • Polyglot Persistence: SQL Server and PostgreSQL — each service uses the best-fit store. Dual-DB strategy: single config flag Api:SqlDatabaseServer switches engine at runtime.
  • Hybrid Authentication: Azure AD (Entra ID) and custom JWT operate side-by-side via a single PolicyScheme selector.
  • Resilient Messaging: MassTransit on PostgreSQL provides transactional outbox semantics — messages are never lost.
  • Observable by Design: Structured NLog logging and event audit trails built-in. CorrelationId/CausationId chain across all services.
  • Configuration-Driven Architecture: Single flag switches DB engine, messaging transport, auth scheme, cache backend, and notification provider — zero code changes required.
  • Field-Level Permission System: [FieldPermission] attribute + FieldPermissionBehaviour + FieldPermissionService provides bidirectional (EDIT + VIEW) field-level ACL with reflection metadata caching per type.
  • Transactional Outbox Reliability: MassTransit PostgreSQL outbox guarantees delivery. 3-retry × 10s policy. Batch consumer for throughput. Dead-letter tracking via FailedMessage.
  • Clean Architecture Discipline: Domain has zero external NuGet refs. Application defines all interfaces. Infrastructure fully swappable — proven by dual-DB strategy.
  • Three-Stage Validation: FluentValidation (syntax) → RulesEngine JSON (business) → Specification Pattern (domain) — complete pipeline without coupling.
  • Pluggable Notification Providers: ZeptoMail API and Microsoft Graph configurable without code changes. MassTransit consumer routes based on message Type field.

3.2 API Gateway — Deep Architecture

The diagram below illustrates the full API Gateway inbound request pipeline. All inbound traffic enters via the Ocelot Gateway. The gateway inspects the Bearer token issuer and delegates to either Azure AD or the custom JWT validator before forwarding the authenticated request downstream.

1
TLS Termination
Accept connection, terminate SSL. HTTPS enforced; HSTS enabled on all services.
2
CORS Enforcement
Validate Origin against allowed-origins policy (WebUrl:AllowOriginApis). Policy: "allowSpecificOrigin". No wildcard origins.
3
Rate Limiting
Token-bucket check per client key. Configured per-route in ocelot.json.
4
Authentication
PolicyScheme MultiAuth: inspects token issuer → routes to AzureAd or DbAuth handler. Clock skew: 0s.
5
Claims Extraction
Append X-Request-Uid (email→preferred_username→unique_name), X-Request-Oid (oid), X-Correlation-Id, X-Request-Id, X-Api-Key, X-Gateway-Start-Ms headers.
6
Authorisation
Policy evaluation on populated ClaimsPrincipal. AzureUsersOnly requires iss claim. DbUsersOnly requires auth_type=db claim.
7
Cache Lookup
Memory / SQL Server response cache lookup before forwarding. Returns cached response if hit.
8
Route Matching
Ocelot downstream config — match path + method. /netcore/{everything} → systemdesign-api.azurewebsites.net/api/{everything}.
9
Request Forwarding
Proxy request to downstream microservice with enriched headers.
10
Response & Compression
Transform response + Gzip / Brotli encoding. Log elapsed time to ApiRequestLog table.

6. Clean Architecture & CQRS

6.1 Dependency Model

Each microservice strictly follows Clean Architecture. The golden rule: dependencies only point inward. Domain is completely infrastructure-agnostic.

6.2 Layer Responsibilities

Every microservice (netcoreapi, netnotificationapi) follows the same four-layer structure. Dependencies point inward — Infrastructure depends on Application, Application depends on Domain, Domain has no external dependencies.

7.4 Custom Field System

Every major entity supports a dynamic custom field system. Fields are stored as a JSON column (CustomFieldJson) in the DB and deserialized to List<CustomField> in C#. Each field carries its own validation metadata:

public class CustomField {
    public string field_name         { get; set; }  // DB column name
    public string display_name       { get; set; }
    public object field_value        { get; set; }  // dynamic value
    public string field_type         { get; set; }  // text, number, date, ...
    public int    field_length       { get; set; }
    public bool   field_is_required  { get; set; }
    public string field_defaultValue { get; set; }
    public string regex              { get; set; }  // validation regex
}

Database schemas are version-controlled and automatically applied at service startup using DbUp. Scripts stored under /Infrastructure/Persistence/BuildScripts/Scripts/ with naming convention: YYMMDD-{Seq}-{Description}.sql. The InitialSetUpController endpoint triggers schema bootstrap on demand.

12. Non-Functional Characteristics

Scalability

  • Horizontal Scaling: Stateless services (no in-process session state) — scale out via Azure App Service plan with zero config changes.
  • Async Messaging: MassTransit PostgreSQL outbox decouples producers from consumers — burst traffic absorbed naturally. Batch consumer: 20 messages per 20-second window.
  • Caching: HybridCache (L1+L2) + pluggable backends. CachingBehaviour auto-caches MediatR query results via [CacheQueryResponse].

Resilience

  • Retry Strategy: MassTransit: UseMessageRetry(r => r.Interval(3, TimeSpan.FromSeconds(10))). 3 attempts before dead-letter.
  • Transactional Outbox: Messages committed atomically with business transaction — guaranteed delivery even if consumer offline.
  • Background Service Isolation: HostOptions.BackgroundServiceExceptionBehavior = Ignore — background service crash doesn't bring down the host.

Security

  • Authentication: Dual-scheme (Azure AD Entra ID + HS256 JWT) via MultiAuth PolicyScheme. ClockSkew = 0s.
  • Authorization: 3-tier: API-level gateway permission → Request-level MediatR behavior → Field-level reflection attribute enforcement.
  • Data Protection: HTTPS enforced; Brotli/Gzip compression; BCrypt.Net-Next 4.1.0 for password hashing.

Maintainability

  • Modularity: Clean Architecture + CQRS. Domain has zero external NuGet dependencies. New features follow same pattern without touching existing code.
  • Testability: All dependencies injected via interfaces. Application layer has no infrastructure references — fully unit-testable with mock implementations.
  • Configuration Management: DB engine, transport, auth scheme, notification providers, cache backends — all runtime-switchable via single config flags. No code changes required.
  • Rule Externalisation: Business rules in JSON files (RulesEngine 6.0.0). No redeployment for rule changes — restart required.
  • SQL Externalisation: All SQL in XML files per entity per DB dialect. Adding a query = update XML only. No recompile.
