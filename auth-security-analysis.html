03 — MultiAuth Scheme Selector Logic
🔀

DependencyInjection.cs — ForwardDefaultSelector (Lines 62–84)

// Registered as the default authentication scheme
services.AddAuthentication("MultiAuth")
  .AddPolicyScheme("MultiAuth", "MultiAuth", options =>
  {
      options.ForwardDefaultSelector = context =>
      {
          string authorization = context.Request.Headers[HeaderNames.Authorization];

          if (!string.IsNullOrEmpty(authorization) && authorization.StartsWith("Bearer "))
          {
              var token = authorization.Substring("Bearer ".Length).Trim();
              var jwtHandler = new JwtSecurityTokenHandler();
              var jwt = jwtHandler.ReadJwtToken(token);

              // Route to Azure AD if Microsoft STS issuer detected
              if (jwt.Issuer.StartsWith("https://sts.windows.net"))
                  return "AzureAd";
          }
          // Fall through to database JWT validation
          return "DbAuth";
      };
  })
  .AddMicrosoftIdentityWebApi(Configuration, "AzureAd", jwtBearerScheme: "AzureAd")
  .EnableTokenAcquisitionToCallDownstreamApi()
  .AddInMemoryTokenCaches();

services.AddJwtBearer("DbAuth", options => {
    options.TokenValidationParameters = new TokenValidationParameters {
        ValidateIssuerSigningKey = true,
        ValidateIssuer          = true,
        ValidateAudience        = true,
        ValidateLifetime        = true,
        IssuerSigningKey        = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(jwtKey))
    };
});

05 — Refresh Token Lifecycle
🔄

Token Lifecycle Flow

🔐
Login — POST /api/v{version}/Auth/login Issues access token (1h) + refresh token (7d, stored in DB)
⏱️
Access Token Expires Client detects 401 and uses refresh token to get new credentials

Gateway AuthorizationMiddleware.cs — ACL Check (Lines 16–38)

public async Task InvokeAsync(HttpContext context, RequestDelegate next)
{
    // Only enforce on /gateway/* routes
    if (!context.Request.Path.Value.Contains("gateway"))
    {
        await next(context);
        return;
    }

    // Require X-Request-Uid to be present
    var uid = context.Request.Headers["X-Request-Uid"].ToString();
    if (string.IsNullOrEmpty(uid))
    {
        context.Response.StatusCode = 401;
        return;
    }

    // Check permission via cached NetAuth service
    var hasPermission = await _authorizationService
        .HasPermissionAsync(uid, context.Request.Path);

    if (!hasPermission) { context.Response.StatusCode = 403; return; }

    await next(context);
}

10 — Field-Level Permission System
🔏

Field Permission Architecture — FieldPermissionBehaviour<TRequest, TResponse>

Field-level access control enforces view and edit permissions at individual entity property granularity. The system is attribute-driven: properties decorated with [FieldPermission] are intercepted by the MediatR pipeline behavior in two phases — edit validation before the handler runs, and view masking after it returns. A concurrent reflection cache ensures type scanning is paid only once per type at startup.

FieldPermissionAttribute.cs

// Domain/Common/FieldPermissionAttribute.cs
[AttributeUsage(AttributeTargets.Property,
    AllowMultiple = false, Inherited = true)]
public class FieldPermissionAttribute : Attribute
{
    public string? ViewPermission { get; }
    public string? EditPermission { get; }

    // true  → throw ValidationException on edit denial
    // false → silently revert to original DB value
    public bool    ThrowError      { get; }

    public FieldPermissionAttribute(
        string? view      = null,
        string? edit      = null,
        bool    throwError = false) { ... }
}

// Usage on a domain entity property
[FieldPermission(
    view: "Core.Policy.TotalPremium.View",
    edit: "Core.Policy.TotalPremium.Edit",
    throwError: false)]
public decimal? TotalPremium { get; set; }
✏️

Phase 1 — Edit Enforcement (Pre-Handler)

Scans TRequest properties for [FieldPermission(edit:...)], fetches the user's granted permissions, then applies the following logic matrix:

View ✔ & Edit ✔
Allow — field accepted
View ✗ & Edit ✗
Silent ignore — field invisible to user
View ✔ & Edit ✗
Error / revert — controlled by throwError
View ✗ & Edit ✔
Throw — suspicious permission state
👁️

Phase 2 — View Masking (Post-Handler)

// FieldPermissionBehaviour.cs — post-handler phase
private async Task MaskViewPermissions(TResponse response)
{
    var props = GetViewProperties(typeof(TResponse));

    foreach (var descriptor in props)
    {
        bool canView = await _currentUser
            .HasPermissionAsync(descriptor.ViewPermission);

        if (!canView)
        {
            // Null out the property — field hidden from client
            descriptor.PropertyInfo.SetValue(response, null);
        }
    }

    // Recursive masking for collection properties
    MaskCollectionItems(response, props);
}

Manual Service Enforcement Pattern

// Handler using IFieldPermissionService directly
public async Task<PolicyDto> Handle(GetPolicyByIdQuery request, ...)
{
    var entity = await _policyData.GetPolicyById(request.Id);

    // Mask view-restricted fields before mapping to DTO
    if (entity != null)
        await _fieldPermissions.ApplyViewPermissionsAsync(entity);

    return _mapper.Map<PolicyDto>(entity);
}

// Update handler — enforce edit permissions
public async Task<Unit> Handle(UpdatePolicyRequest request, ...)
{
    var original = await _policyData.GetPolicyById(request.Policy.Id);

    // Compare original vs proposed; revert or throw per ThrowError
    await _fieldPermissions.ApplyEditPermissionsAsync(original, request.Policy);

    await _policyData.Update(request.Policy);
    return Unit.Value;
}

15 — Security Findings & Recommendations
✅
Multi-scheme authentication with smart routing
The MultiAuth policy scheme correctly routes tokens to either Azure AD or DbAuth without exposing scheme selection to clients. The selector reads the JWT issuer field before forwarding — a solid pattern for hybrid auth environments.
✅
Refresh token rotation implemented
RefreshTokenDataAccess.RotateAsync() revokes the previous token before issuing a new one. This prevents refresh token reuse attacks and limits exposure if a token is stolen.
✅
Defense-in-depth via layered pipeline
Security is enforced at three independent layers: Ocelot gateway (route-level), Gateway AuthorizationMiddleware (ACL), and MediatR pipeline behaviors (ApiKey + AuthZ + FieldPermission). No single bypass point compromises all layers.
✅
JWT validation parameters fully enabled
All four critical JWT validation flags are enabled: ValidateIssuerSigningKey, ValidateIssuer, ValidateAudience, ValidateLifetime. No weak validation configurations detected.
✅
Field-level access control with dual-phase enforcement
The FieldPermissionBehaviour provides fine-grained property-level security. Edit permissions are checked pre-handler; view masking is applied post-handler. The throwError flag gives per-field control over whether denial is explicit or silent, covering both visible-field and hidden-field scenarios correctly.
✅
Field permissions covered by integration test suite
PolicyTotalPremiumFieldPermissionTest.cs covers all eight enforcement paths (GET/CREATE/UPDATE × view-granted / view-denied / edit-granted / edit-denied combinations), providing confidence that permission logic is correct across all scenarios.
ℹ️
CORS — AllowAnyOrigin() is present alongside WithOrigins() whitelist
In Api/Startup.cs the CORS policy calls .WithOrigins(alloworiginapis) and then .AllowAnyOrigin(). In production, removing .AllowAnyOrigin() tightens the origin restriction to the configured whitelist (msb.azurewebsites.net, stai.azurewebsites.net).
ℹ️
JWT signing key in appsettings.json — move to secrets management for production
The HMAC-SHA256 signing key is currently in appsettings.json. For production deployments, loading it from Azure Key Vault or environment variables (rather than source-controlled config) is the recommended hardening step.
ℹ️
Rate limiting — Ocelot supports it natively if needed
No rate limiting middleware was observed at gateway or microservice level. Ocelot has built-in rate limiting configuration via RateLimitOptions in ocelot.json, and ASP.NET Core 7+ provides Microsoft.AspNetCore.RateLimiting as an in-process option if login/refresh endpoints require protection.
ℹ️
API key comparison — consider constant-time equality for hardened environments
apiKey.Equals(extractedApiKey) in ApiKeyAuthBehaviour.cs is not constant-time. CryptographicOperations.FixedTimeEquals() is available in .NET for environments where timing-side-channel hardening is required.
ℹ️
Azure AD ACL mode — verify app registration access controls
AllowWebApiToBeAuthorizedByACL: true means any valid Azure AD token can call the API without specific app role assignments. Ensure the Entra ID app registration has appropriate access controls configured for the intended audience.
ℹ️
Azure AD ClientId and TenantId in appsettings
The Azure AD ClientId (0f9846e5-...) and TenantId are in appsettings.json. While these are not secrets, environment-specific config (e.g., per-slot app settings in Azure App Service) avoids exposing tenant topology in source control.
